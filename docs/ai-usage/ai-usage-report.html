3. 게임 개발과 검증

AI에게 기능 구현만 요청하지 않고, 플레이 제보와 기획 의도를 실제 코드 경로와 테스트 조건으로 바꾸도록 했습니다. 화면에서 판단할 수 있는 항목은 코드의 추정보다 실제 렌더 결과를 우선했습니다.

3.1 게임플레이와 레벨 디자인

이동 성능, 점프 높이, 발판 간격, 피트와 적의 관계를 실측해 전역 규칙으로 정리했습니다. 그 위에서 스테이지 1~5를 같은 기준으로 검토하고, 3스테이지의 사격을 가리는 공중 발판, 불필요한 세로 벽, 점프로 연결되지 않는 구간을 찾았습니다. 러프 배치는 스테이지별 에이전트가 같은 기준으로 작성하고, 도달성 테스트와 실제 플레이로 최종 확인했습니다.

3.2 코드 리뷰를 탐색과 반증으로 분리

관점별 탐색 → 파일, 라인 단위 후보 수집 → 독립 검증 에이전트의 반증 → 검증된 항목만 보고 → 테스트와 플레이 확인

PR #11에서는 공중 적 3종의 deathAnimationDuration이 0인 채로 남아, 추락, 착지, 페이드 도중 방이 클리어되는 문제가 발견되었습니다. 사망 로직을 CoordinatedAerialEnemy로 통합하고 전체 연출 시간을 처치 지연에 반영했으며, 마지막 적의 사망 중 방이 조기 클리어되지 않는 회귀 테스트를 추가했습니다.

3.3 자연어 플레이 제보를 회귀 테스트로 변환

플레이에서 발견한 현상 추적한 원인과 수정 검증
구덩이에 걸친 적과 정상 지형 끝의 적이 같은 방식으로 추락 구덩이 진입과 가장자리 장벽 충돌을 분리 구덩이 제거, 가장자리 충돌 테스트
보스 레이저가 캐논 발사구와 어긋남 발사 시작점을 방향별 캐논 좌표에 고정하고 각도만 계산 좌우 발사구 좌표와 플레이 화면
방 전환 후 플레이어가 공중에서 멈춤 그랩이 끈 중력을 공통 PlayerController.stop()에서 복원 헤드리스 상태 덤프와 강하 화면
적 처치 시 이미 발사된 탄막까지 사라짐 적과 투사체의 수명을 분리하고 씬 갱신 루프로 인계 분리 갱신과 구독 해제 단위 테스트
화면 파괴 순간 총과 팔이 사라짐 스냅샷 전에 무기 리그를 숨기던 이벤트 순서 수정 전환 회귀 테스트와 실제 연출

3.4 상태와 연출의 시간축 검증

4스테이지 보스 처치 후 흐름은 보스 처치 → 쓰러짐, 소멸 → 1초 유지 → 화면 파괴 → 완료 후 5스테이지 BGM 시작으로 고정했습니다. 서로 다른 시스템에 흩어진 보상, 소멸 콜백, 화면 전환, 음악 이벤트를 순서대로 연결하고 지연 시간과 음악 시작 시점을 테스트했습니다.

4. 에셋 생성과 실제 리소스화

아트의 외형부터 요청하지 않고 코드에서 동작할 전투 패턴을 먼저 정의했습니다. 필요한 자세와 효과를 상태 단위로 역산한 뒤 생성하고, 프레임 일관성과 게임 좌표계를 검증했습니다.

역할, 전투 패턴 → 애니메이션 상태 → 생성 제약 → 이미지 초안 → 오류 검토 → 재생성, Aseprite 보정 → 게임 화면 검수

4.1 게임 로직에서 애니메이션 상태 도출

3스테이지 보스는 플레이어를 끌어당기는 ‘불순물 수거’와 점프 후 지면을 내려찍는 ‘폐기물 압축’을 먼저 정의했습니다. 이후 idle, walk, 도약 준비, 상승, 공중 체공, 하강, 내려찍기, 흡입, 피격, 사망으로 스프라이트 상태를 나눴습니다. 최종 보스도 halo-charge, halo-fire, wings-left, eye-track, phase-transition처럼 코드와 같은 상태명을 사용했습니다.

역할 보스의 끌어당기기 패턴을 미리 학습시키는 구속형 안드로이드

행동 케이블 발사 → 플레이어 끌어오기 → 근거리 전기 충격

출력 idle 1장 / walk 2장 / attack 2장 / hit 1장 / death 1장

제약 크기, 중심점, 장비 위치, 팔다리 굵기, 좌우 방향 유지

검증 걷기 프레임의 다리 교차, 외곽 잘림, 소품 개수 변화 확인

4.2 프레임 일관성과 플레이 공간을 함께 지정

애니메이션 조건
  • 프레임별 크기와 중심점 고정
  • 장비 개수와 팔다리 굵기 유지
  • 이전과 다음 프레임의 자세 연결
  • 잘림 방지를 위한 외곽 여백 확보
게임플레이 조건
  • 적 이동 경로와 배경 레이어 고려
  • 1280×720 화면에서 캐릭터 배치 공간 확보
  • 공격 판정과 효과 스프라이트 기준점 일치
  • 플레이어보다 앞이나 뒤에 그려질 순서 지정

천장 파이프는 매달린 적의 이동을 가리지 않도록 연결부와 아래쪽 실루엣을 낮췄습니다. 배경은 분위기만 지정하지 않고 다음 연출에서 캐릭터가 들어갈 중앙 공간을 비우도록 요청했습니다. 3스테이지 보스의 흡입 효과는 보스의 흡입구를 기준으로 높이와 길이를 계산하고, 플레이어가 효과보다 앞에 보이도록 레이어를 조정했습니다.

4.3 생성 결과를 최종 리소스로 만드는 과정

  1. 관절, 손, 다리, 장비, 프레임 비율 오류 확인
  2. 문제를 포즈 스케치나 픽셀 단위 지시로 구체화해 재생성
  3. Aseprite에서 축소, 도트, 실루엣 정리, 중심점과 투명 영역 보정
  4. 실제 게임에서 애니메이션, 좌표, 레이어와 공격 판정 확인
  5. 통과한 결과만 게임 리소스와 상태 머신에 연결

4.4 무기 합성 실패를 런타임 구조로 해결

손과 총을 이미지 생성으로 합치자 양쪽 원본 픽셀이 다시 그려졌습니다. 이를 앞팔, 손, 총, 뒷팔의 세 조각으로 나누고 런타임에서 같은 각도로 회전시키는 구조로 변경했습니다. 네 총기의 손잡이는 공통 손 위치에 픽셀 단위로 맞추고 캐릭터, 배경 합성 미리보기로 검수했습니다. 위치만 바꿔 해결할 수 없던 버스트 라이플은 짧은 불펍형으로 다시 제작해 게임 규칙에 아트를 맞췄습니다.

5. 반복 작업을 위한 커스텀 Skill

같은 문제를 매번 긴 프롬프트로 설명하지 않도록 프로젝트 전용 Skill을 제작해 Codex에 등록했습니다. AI의 시각 추론과 스크립트의 결정적 처리를 분리해 결과의 재현성과 안전성을 높였습니다.

5.1 transparent-character-png

ChatGPT로 생성한 픽셀아트에 투명 배경이 없을 때 사용합니다. 이미지 편집 생성으로 배경을 지우면 캐릭터가 재창조되고, 초록색, 마젠타색 크로마 제거만 사용하면 테두리 잔색이나 내부 색상 손실이 생겼습니다. Skill은 AI 결과를 최종 이미지가 아닌 후보 알파 마스크로만 사용하도록 제한합니다.

핵심 불변 조건: 최종 PNG의 RGB는 원본과 픽셀 단위로 같아야 하며, 변경할 수 있는 것은 알파 채널뿐입니다.

scripts/apply_alpha_to_original.py는 원본과 후보의 크기, 저장 전후 RGB 일치, 전체 불투명, 전체 투명 여부, 캔버스 테두리의 실제 투명 영역을 검사합니다. 기존 알파는 새 알파와 결합하고, 원본과 후보 파일의 덮어쓰기를 막습니다. 검정, 흰색, 체크무늬 배경 미리보기와 알파 마스크로 테두리와 내부 구멍도 확인합니다.

발견한 실패 최종 반영을 막은 기준
검은 배경 제거가 캐릭터의 검은 갑옷까지 삭제 캔버스 경계와 연결된 배경만 우선 제거하고 내부 영역 복원
흰 배경과 비슷한 장갑이 반투명해짐 외부 배경은 유지하되 닫힌 내부 영역의 알파만 교정
AI 프록시가 원본보다 1px 작거나 외곽선이 이동 리사이즈, 자동 정렬하지 않고 결과 폐기 후 원본 기반 추출

5.2 soot-ui-pixel-art

기존 hatch-pet Skill에서 픽셀 그리드, 투명도, 상태 간 일관성, 실제 크기와 확대 미리보기 검증 원칙만 추출했습니다. 여기에 Soot의 어두운 산업형 팔레트, HUD, 패널, 버튼 유형, 상태별 에셋, 나인슬라이스, React, CSS, Phaser의 책임 분리, 1280×720과 모바일 구간의 접근성 검증을 추가했습니다.

실제 적용 Skill을 이용한 판단과 수정 검증
조작 가이드 상시 문구를 ? 버튼과 3×3 모달로 분리 Playwright로 배치, 닫기 경로, 텍스트 넘침 확인
픽셀 UI 상태 27×27 원형 버튼의 기본, 호버 외곽선을 별도 제작 실제 크기와 확대 화면 비교
보스 HUD 체력 숫자는 숨기고 접근성용 meter 속성은 유지 SSR 결과와 E2E 위치 검사
2스테이지 포탈 새 이미지 대신 선택적 portalTint로 대비만 개선 브라우저, 설정 테스트, 타입, lint, build

두 Skill은 단순한 프롬프트 모음이 아닙니다. 반복 실패를 분석해 AI 추론 → 결정적 스크립트 처리 → 시각 검수 → 게임 적용 순서와 통과 조건을 도구화한 결과입니다.

6. 생성형 오디오 운용

Lyria로 음악을 만드는 것보다 후보를 추적하고 사람이 비교해 선택할 수 있게 만드는 데 더 많은 자동화를 적용했습니다.

6.1 프롬프트와 테이크 추적

스테이지 정서를 악기, 음색, BPM, 반복 구조로 구체화하고 큐별 프롬프트 버전과 전체 테이크 번호를 함께 관리했습니다. 5스테이지는 프롬프트 A23, 전체 69번 테이크까지 진행했습니다. 각 후보의 프롬프트, 측정값, 반려 이유는 docs/audio-assets.md에 기록했습니다.

dark orchestral, low unsteady cello and viola, distorted electric guitar arpeggio, detuned and grinding, sparse slow drum kit, familiar but wrong, purely instrumental, loopable background bed, 88 BPM, D minor

6.2 측정은 비교 자료, 채택은 청취

tools/audio-check.html은 전체 후보를 한 화면에서 A/B 재생할 수 있게 만들었습니다. “추천”은 측정 기준을 통과했다는 의미일 뿐이며, 기본 화면은 “전체”입니다. 대역 목표가 사람의 평가를 예측하지 못한 뒤에는 프롬프트를 고정하고 테이크 수를 늘려 두 사람이 직접 듣고 선택했습니다.

자동화 역할 사람이 유지한 판단
measure-track.mjs 페이드, 대역, BPM, 이음매 측정 측정값이 정서와 곡의 완성도를 대신하지 않음
audio-check.html 후보 전체 비교와 A/B 청취 자동 탈락 후보도 다시 듣고 채택 가능
make-loop.mjs 페이드, 크로스페이드와 루프 렌더 실제 이음매를 듣고 구간과 곡선 확정
make-gunshot.mjs 총성 효과음 결정적 합성 게임에서의 음량과 타격감 검수

예상과 측정이 틀린 사례도 기록했습니다. 밝은 도시의 기준을 지하도시 큐에 적용하자 모든 후보가 탈락했고, 총소리와 충돌한다고 가정한 1~4kHz도 실제 총성의 중심 대역과 달랐습니다. 두 항목은 합격 판정에서 제거하고 정보로만 표시했습니다. 5스테이지 루프에서는 등파워 크로스페이드가 이음매를 1.6dB 키워 실제 렌더 청취 후 리니어 곡선을 선택했습니다.

6.3 게임 상태와 효과음의 시간축 연결

2스테이지 보스의 스캔은 시작음, 반복음, 타깃 고정음, 종료음으로 나누고 취소나 씬 전환 시 반복음을 정리했습니다. 3스테이지 보스의 내려찍기는 예고, 도약, 충돌, 착지 잔향을 각 상태 전이에 맞췄습니다. 발소리는 스테이지 재질별로 변주하되 공중전인 5스테이지에서는 끄고, 방패와 무적 판정은 일반 피격음과 다른 이벤트로 구분했습니다.

7. 에이전트 운용과 Human-in-the-loop

7.1 작업 기준을 도구 바깥에 고정

AI를 저장소에 접근하는 작업자로 사용했기 때문에 작업 범위와 문체, 안전 규칙을 AGENTS.md에 기록했습니다. 코드 주석은 한국어, 식별자와 로그는 영어로 유지하고, 새 코드는 주변 코드 스타일을 따르게 했습니다. 승인이나 병합처럼 되돌리기 어려운 동작은 사람의 요청 없이 수행하지 않도록 고정했습니다.

7.2 작업 분리와 실제 실행

오디오, 레벨, 무기, 문서 작업은 워크트리로 분리했습니다. 서로 독립적인 스테이지 러프 배치는 같은 level-design 기준을 받은 서브 에이전트에 나누고 결과를 사람이 비교했습니다. 정적 설정만으로 판단하기 어려운 배치는 에이전트가 개발 서버를 열고 어드민 이동과 무적 모드로 직접 확인했습니다.

7.3 공통 작업 흐름

  1. 요구와 기획 의도를 기능 단위로 분해
  2. 관련 코드, 설정, 커밋에서 실제 동작 경로 확인
  3. 대안, 위험 요소, 테스트 항목을 AI와 검토
  4. 코드, 에셋, 오디오를 수정하고 자동 검사 실행
  5. 팀원이 실제 플레이, 화면, 청취로 최종 검수
  6. 통과한 내용만 커밋과 문서에 반영
AI 탐색과 반복을 가속

호출 경로 탐색, 대안 제시, 초안 생성, 수치 계산, 반복 처리, 테스트 항목 도출을 맡았습니다.

Human 맥락과 최종 책임 유지

기획 목표, 시각, 청각 품질, 승인, 병합, 최종 리소스 채택을 직접 결정했습니다.

8. 한계와 대응

확인된 한계 대응 원칙
모호한 지시를 임의로 해석해 무관한 브랜치를 병합 되돌리기 어려운 동작은 해석이 갈리면 실행 전에 질문
요청하지 않은 PR 승인과 게시 코멘트 수정 승인과 병합, 외부 게시물 수정은 사람의 명시적 권한 유지
코드상 같은 값이라는 이유로 실제 화면 차이를 부정 화면에서 확인 가능한 항목은 플레이 캡처와 육안 검수 우선
이미지 생성이 원본 픽셀과 장식을 재창조 AI는 마스크와 초안만 생성하고 원본 보존은 스크립트로 검증
한 번의 코드 리뷰가 총구와 발사음 문제를 놓침 관점별 탐색과 독립 반증 단계로 리뷰 구조 변경
측정값이 음악에 대한 사람의 선호를 예측하지 못함 측정은 비교 정보로만 사용하고 전체 후보를 사람이 청취
같은 오디오 측정을 브라우저와 스크립트에 중복 구현 측정 구현을 한 모듈로 통합하고 UI는 결과만 표시

9. 결과물과 외부 에셋의 구분

구분 출처와 처리 최종 사용 기준
이미지 ChatGPT 이미지 생성과 SpriteCook 초안을 Aseprite와 전용 Skill로 가공 크기, 프레임, 좌표, 레이어, 투명도 검수 후 적용
BGM Gemini 앱의 Lyria 후보를 루프 편집하고 Ogg/Opus로 변환 프롬프트와 테이크를 기록하고 사람이 청취해 채택
효과음 Kenney CC0 에셋 또는 저장소 스크립트로 자체 합성 큐별 출처를 docs/audio-assets.md에 기록
오픈소스 Phaser, React, Zustand, Vite, TypeScript, Vitest, Playwright 등 설치된 패키지의 버전과 MIT 및 Apache-2.0 라이선스 확인

Kenney 효과음 팩 3종은 License.txt에서 CC0 1.0을 확인했고, 표기 의무는 없지만 크레딧을 남깁니다. Lyria는 소비자용 Gemini 앱에서 생성했으며, 특정 아티스트나 곡을 모방하는 이름은 프롬프트에 넣지 않았습니다. 생성 트랙의 SynthID 워터마크는 제거하지 않았습니다. 이미지 생성물과 외부 에셋의 이용 범위는 제출 전 해커톤 규정과 각 서비스 약관을 다시 확인합니다.

10. 활용 효과와 최종 정리

탐색 비용 절감

스테이지, 적, 보스, 배경과 오디오의 여러 방향을 빠르게 비교했습니다.

구현 근거 명확화

기획 문장을 상태, 이벤트, 좌표, 테스트 조건으로 변환했습니다.

반복 절차 표준화

투명화, UI 제작, 리뷰와 오디오 측정을 Skill, 스크립트로 고정했습니다.

검증 가능성 확보

코드, 커밋, 에셋 해시, 테이크 기록과 자동 테스트를 근거로 남겼습니다.

본 프로젝트에서 AI는 게임을 자동으로 완성하는 도구가 아니라, 개발자가 정한 게임 규칙을 빠르게 구체화하고 반복 검증하는 제작 보조 도구였습니다. 판단 기준은 저장소 규약과 Skill에 고정했고, 생성 결과는 결정적 스크립트와 자동 테스트로 검사했습니다. 최종 코드, 도트, 음악과 플레이 경험은 팀원이 실제 게임에서 확인한 뒤 채택했습니다.

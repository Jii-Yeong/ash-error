# AI 활용 내역

> Codex와 Claude Code를 게임 기획, 구현 보조, 레벨 디자인, 코드 리뷰, QA, 오디오 제작, 문서화에 활용했습니다. ChatGPT와 이미지 생성 기능은 아트 콘셉트와 게임 에셋 초안 제작에 활용했습니다. 반복 작업은 프로젝트 목적에 맞는 커스텀 Skill과 검증 스크립트로 표준화했고, 판단 기준은 저장소의 `AGENTS.md`에 고정했습니다. 코드 리뷰는 관점을 나눈 다중 탐색과 지적별 반증 검증을 거쳐 통과한 항목만 사람에게 전달하도록 구성했으며, 승인과 병합은 사람이 수행했습니다. AI의 제안과 생성 결과는 팀원이 코드와 실제 플레이를 확인한 뒤 반영했습니다.

### 1.1 에셋 생성 AI 활용 개요

본 프로젝트에서는 생성형 AI를 단순 결과물 생성 용도가 아니라 다음 과정에 활용했습니다.

**게임 기획 구체화 → 아트 콘셉트 설계 → 애니메이션 스프라이트 초안 생성 → 결과 검증 → 수정 지시 → 실제 게임 리소스화**

동일 캐릭터의 여러 애니메이션을 제작해야 하는 2D 횡스크롤 게임의 특성상, AI에게 단순히 "캐릭터를 그려줘"라고 요청하지 않고 다음 정보를 구조화해 전달했습니다.

- 캐릭터의 역할과 전투 목적
- 공격 패턴과 실제 게임 로직
- 필요한 애니메이션 상태
- 프레임 간 연결 조건
- 캐릭터의 비율과 방향
- 색상과 장식의 일관성
- 투명 배경 여부
- 게임 내 실제 스프라이트 크기
- 잘림, 관절 오류, 소품 변경 여부 등의 검증 조건

AI 출력물은 그대로 최종 리소스로 사용하지 않았습니다. Aseprite에서 크기 조절, 도트 정리, 실루엣 보정, 프레임 연결, 애니메이션 확인을 거쳐 최종 리소스로 제작했습니다.

## 2. 사용 AI 도구

### 2.1 Codex·Claude Code

두 도구 모두 저장소에 직접 접근하는 터미널 에이전트 형태로 사용했습니다. 공통 활용은 다음과 같습니다.

- 게임 기획과 현재 구현 비교
- 관련 코드와 호출 경로 탐색
- 게임플레이 구현 및 리팩터링 보조
- 레벨 설정과 도달 가능성 검토
- PR과 브랜치 변경사항 리뷰
- 테스트 시나리오 작성과 실행 결과 분석
- 커밋·기능 단위 문서화

역할은 완전히 겹치지 않게 나누어 사용했습니다.

| 도구 | 주로 맡긴 작업 |
| --- | --- |
| Codex | `level-design` 기준의 스테이지 배치 재구성, 설정 UI 구축, 서브 에이전트를 이용한 3~5스테이지 러프 배치, Chrome DevTools MCP로 실제 게임 화면 확인 |
| Claude Code | 멀티 에이전트 코드 리뷰와 PR 코멘트 작성, 무기 스프라이트 정렬·합성, 브라우저 자동화 기반 BGM 생성 운용, 오디오 측정·가공, 문서화 |

같은 문제를 두 도구에 교차로 물어 한쪽의 결론을 다른 쪽이 검증하도록 한 사례는 7장에 정리했습니다.

### 2.2 ChatGPT

- 스테이지와 보스 전투 패턴 설계
- 적 역할과 전투 방식 설계
- 필요한 애니메이션 상태 정의
- 스프라이트 제작용 프롬프트 구조화
- 생성 결과의 문제점 분석
- Aseprite 작업 방법과 스프라이트 제작 과정 보조
- 배경, 발판, 환경 오브젝트 콘셉트 설계

### 2.3 ChatGPT 이미지 생성 기능

- 보스와 일반 몬스터 콘셉트 아트 초안
- 공격, 피격, 사망 등 상태별 스프라이트 초안
- 스테이지별 바닥과 플랫폼 초안
- 스테이지 전환용 환경 이미지 초안
- 게임 연출용 배경 초안

### 2.4 Lyria

- 스테이지 분위기에 맞는 BGM 후보 생성
- 조성, 악기, 음색, BPM, 반복 구조를 반영한 음악 탐색

### 2.5 transparent-character-png

- 캐릭터 이미지의 외부 배경만 제거하는 비파괴 투명화
- 생성 결과가 아닌 원본 이미지의 RGB를 그대로 유지하고 알파 채널만 적용
- 초록색·마젠타색 배경 테두리와 내부 투명화 오류 검증
- 원본 보존과 반복 가능한 결과를 위한 `apply_alpha_to_original.py` 실행

### 2.6 soot-ui-pixel-art

- Soot의 어두운 산업형 픽셀아트 UI 제작 기준 정의
- HUD, 체력바, 버튼, 패널, 경고, 프롬프트, 커서, 아이콘의 상태별 에셋 제작
- 프로젝트 팔레트, 실제 렌더링 크기, 투명도, 픽셀 그리드, 반응형 UI 검증
- React·CSS·Phaser가 담당할 동적 요소와 이미지 에셋으로 제작할 정적 요소 구분

### 2.7 level-design·game-ui-ux·find-skills

에셋 제작용 Skill 외에, 개발 판단 기준을 고정하기 위한 공개 Skill도 설치해 사용했습니다.

- `$level-design`: 블록아웃, 플레이어 이동 지표, 페이싱, 게이팅, 인카운터 설계 기준으로 스테이지 1~5의 발판·벽·구덩이·적 배치를 반복 점검
- `$game-ui-ux`: 앵커 기반 반응형 배치, 화면 스택, 포커스 이동 기준으로 설정 화면과 일시정지 화면 점검
- `$find-skills`: 필요한 기준이 이미 Skill로 존재하는지 먼저 검색한 뒤 설치

같은 판단을 매번 새 프롬프트로 설명하지 않고 Skill 호출로 대체해, 스테이지마다 다른 기준이 적용되는 것을 막았습니다.

### 2.8 브라우저 자동화와 MCP

- Chrome DevTools MCP: 에이전트가 개발 서버를 직접 열고 어드민 스테이지 이동과 무적 모드로 각 방의 실제 배치를 화면에서 확인
- 브라우저 자동화: Gemini 웹의 Lyria 생성 화면을 에이전트가 직접 조작해 프롬프트 제출과 생성 완료 대기를 반복

정적 분석만으로 확인할 수 없는 항목은 도구가 실제 화면에서 확인하도록 했습니다.

## 3. 분야별 활용 내역

### 3.1 게임 기획·설계

기획서의 스테이지 분위기와 캐릭터 변화를 읽고, 이를 플레이어 이동과 전투 흐름으로 번역하는 데 활용했습니다. 특히 5스테이지를 단순한 수직 이동이 아니라 지상에서 공중전으로 넘어가는 전환 연출로 구체화했습니다.

AI는 기획 의도를 제안하는 데 그치지 않고 현재 코드의 실제 호출 경로와 비교하는 역할을 했습니다. 기획과 구현이 어긋나는 지점은 팀원이 최종 판단하고 코드와 테스트에 반영했습니다.

### 3.2 게임플레이 구현 보조

비행 진입, 포탈 전환, 플레이어 바디 동기화, 원거리 적의 순찰과 피트 경계를 대상으로 관련 클래스와 이벤트 흐름을 탐색했습니다. 이를 통해 수정 대상과 검증해야 할 상태를 분리했습니다.

주요 활용 결과는 `flightEntryJump` 단위 테스트, 포탈 진입 경로 보강, 관리자 스테이지 직행 경로 점검입니다. AI가 작성한 코드를 그대로 사용하지 않고 기존 구조와 테스트 기준에 맞춰 팀원이 수정·확정했습니다.

### 3.3 레벨 디자인·QA

스테이지 1~5의 룸 설정을 비교해 플레이어 점프 높이, 발판 간격, 벽 배치, 피트와 적의 관계를 점검했습니다. 정적 분석 결과는 실제 플레이에서 확인할 QA 항목으로 바꾸었습니다.

그 결과 3스테이지 공중 발판이 지상 적에 대한 사격을 가리는 문제, 불필요한 세로 벽, 점프로 연결되지 않는 구간을 식별했습니다. 레벨 회귀 테스트와 도달 가능성 테스트로 수정 결과를 확인했습니다.

### 3.4 코드 리뷰·회귀 검증

무기 스프라이트, 총구 위치, 반동, 투사체 생성, 스테이지 설정 변경을 PR 단위로 검토했습니다. 변경 파일만 보는 대신 씬 재시작, 물리 바디, 투사체 풀, 관리자 직행 경로가 기존 상태와 충돌하는지 확인했습니다.

검토 결과는 관련 Vitest와 Playwright E2E, TypeScript 검사, lint, build 결과로 확인했습니다. PR의 승인 여부보다 변경 범위와 실행 결과를 중심으로 판단했습니다.

리뷰를 여러 에이전트로 나누어 실행하고 지적마다 반증 단계를 붙인 구조와 실제 적용 사례는 7장에 정리했습니다.

### 3.5 에셋 생성

아트의 외형만 요청하지 않고 실제 코드에서 동작할 공격 패턴을 먼저 정의했습니다. 이후 해당 패턴에 필요한 자세를 역으로 도출해 이미지 생성 프롬프트에 반영했습니다.

한 장의 완성도보다 프레임 간 일관성을 중요하게 다뤘습니다. 캐릭터 크기, 중심점, 장비 위치, 팔과 다리 굵기, 좌우 방향, 프레임 여백을 반복해서 명시했습니다.

생성 결과는 직접 검토하고 구체적인 오류를 수정 요청했습니다. 관절, 손가락 수, 장비 형태, 프레임별 비율이 달라진 경우 재생성하거나 Aseprite에서 직접 보정했습니다.

캐릭터·배경과 달리 무기는 런타임에서 팔과 함께 회전하는 구조라 정렬 문제가 별도로 발생했습니다. 그 과정은 8장에 정리했습니다.

### 3.6 오디오 제작

오디오는 전체 AI 활용 중 하나의 분야로 다뤘습니다. Lyria로 스테이지 분위기에 맞는 후보를 생성하고, 레벨·템포·주파수·루프 특성을 측정한 뒤 실제 청취와 함께 최종 후보를 골랐습니다.

선별한 음원은 페이드와 크로스페이드를 편집하고 Ogg/Opus로 변환한 뒤 `AudioDirector`와 이벤트 계약에 연결했습니다. 효과음은 CC0 에셋 선별 또는 자체 합성으로 구성해 BGM 생성과 구분했습니다.

테이크 생성 자동화, 후보 심사 도구, 측정 스크립트, 포맷과 로딩 전략의 결정 근거는 9장에 정리했습니다.

### 3.7 문서화

커밋 기록과 세션에서 확인된 작업을 게임 기능, AI 활용, 팀 역할로 분류했습니다. 세션의 내부 식별자나 계정 설정 같은 작업 로그는 제외하고, 제출에 필요한 활용 목적·작업 방식·검증 결과만 남겼습니다.

## 4. 에셋 생성 AI 활용 방식

### 4.1 게임 로직을 먼저 정의한 뒤 아트 생성

예를 들어 3스테이지 보스는 다음 게임 로직을 먼저 정의했습니다.

#### 게임 패턴

- 불순물 수거
  - 플레이어 위치에 경고 표시
  - 청소기 형태의 팔로 플레이어를 끌어당김
  - 공중 상태에서는 잡히지 않음
  - 대시를 이용해 탈출 가능
- 폐기물 압축
  - 보스가 점프
  - 공중에서 낙하
  - 지면을 내려찍음
  - 바닥을 따라 압력파 발생

이후 필요한 스프라이트를 상태 단위로 분리해 AI에 요청했습니다.

#### 실제 활용 프롬프트 예시

> 이 그림을 이용해서 3스테이지 보스의 픽셀아트를 생성해줘.
> 그림의 비율을 맞춰서 만들어줘.
>
> - idle 1장
> - walk 3장
> - 공중에 뜨려고 몸을 낮춘 모션 1장
> - 공중에 점프해서 위로 올라가면서 다리가 아래로 모아진 모션 1장
> - 공중에 떠있는 모션 1장
> - 공중에서 내려가는 모션 1장
> - 땅을 내려찍는 모션 1장
> - 청소기로 빨아들이는 모션 1장
> - 타격 받은 모션 1장
> - 쓰러진 모션 1장
>
> walk 3장은 이어붙였을 때 어색하지 않도록 하고,
> 다리 관절이 실제로 움직이는지 검토해줘.
>
> 청소기로 빨아들이는 모션은 원본의 원형 청소기 구조를 유지해줘.
>
> 각 픽셀아트는 그림체와 색깔 톤이 같고,
> 서로 이어졌을 때 어색하지 않은지도 검토해줘.

공격 패턴을 기준으로 애니메이션 목록을 먼저 구성해 필요하지 않은 스프라이트 제작을 줄였습니다. 프로그래밍 상태 머신과 그래픽 리소스의 대응 관계도 명확하게 만들었습니다.

### 4.2 애니메이션 조건을 포함한 프롬프트

게임 스프라이트는 한 장의 완성도보다 여러 프레임 사이의 일관성이 중요합니다. 따라서 다음 조건을 반복적으로 명시했습니다.

- 프레임별 캐릭터 크기 동일
- 중심점 동일
- 장비 위치 동일
- 팔과 다리 굵기 동일
- 좌우 방향 유지
- 이전 프레임에서 다음 프레임으로 자연스럽게 연결
- 프레임 가장자리에서 캐릭터가 잘리지 않도록 여백 확보

#### 실제 활용 프롬프트 예시

> 3스테이지 잡몹 구속형 안드로이드 픽셀아트를 그려줘.
>
> 지하에 숨어 있는 인간을 죽이기보다 붙잡아 끌어내는 용도로
> 개조된 안드로이드야.
> 3스테이지 보스의 '불순물 수거' 패턴을 미리 학습시키는 잡몹 역할도 해.
>
> 필요한 모션:
>
> - idle 1장
> - 케이블 발사 모션 1장
> - walk 2장
> - 가까이 끌어왔을 때 전기 충격 공격 모션 1장
> - 타격 모션 1장
> - 쓰러진 모션 1장
>
> walk는
> 한 장은 왼발이 앞으로,
> 한 장은 오른발이 앞으로 오게 만들어줘.
> 두 프레임을 이어붙였을 때 자연스럽게 걸어야 해.
>
> 각 그림의 그림체를 통일하고,
> 팔과 다리는 일정한 굵기를 유지해줘.
> 케이블 장치와 등에 달린 장비 등의 소품이
> 프레임마다 바뀌지 않았는지도 검토해줘.
>
> 모든 프레임의 비율과 캐릭터 크기가 동일한지도 확인해줘.

단순 그림 생성뿐 아니라 프레임 간 일관성 검토까지 AI에 요청했습니다.

### 4.3 출력 결과 검증과 반복 수정

AI 생성 결과를 그대로 사용하지 않고 출력물을 직접 검토한 뒤 구체적인 오류를 찾아 수정 요청했습니다.

#### 사례 1. 인체·관절 오류 수정

초기 생성 결과에서 걷기 애니메이션의 다리 관절이 자연스럽지 않아 직접 간단한 포즈 스케치를 제작해 AI에 전달했습니다.

> 다리 모양을 내가 낙서한 것처럼 참고해서 고쳐줘.
> 원본 캐릭터의 비율은 그대로 유지해줘.
> 두 걷기 프레임에서 다리가 실제로 교차하며 움직이는지 검토해줘.

AI의 추상적인 자세 해석에만 의존하지 않고 팀원이 직접 포즈 레퍼런스를 전달해 원하는 애니메이션 방향을 통제했습니다.

#### 사례 2. 환경 오브젝트와 게임플레이의 관계 고려

3스테이지에는 천장 파이프를 따라 이동하는 적이 있습니다. 초기 파이프 이미지에서는 연결부가 지나치게 튀어나와 몬스터가 이동할 때 그래픽이 겹쳐 보일 가능성이 있었습니다.

> 이음새가 너무 튀어나와 있어서
> 몬스터가 지나가면 이음새가 몸 앞으로 보일 것 같아.
>
> 연결부를 파이프 본체와 거의 같은 굵기로 낮춰줘.
> 파이프 아래쪽 실루엣은 최대한 평평하게 유지해서
> 매달린 몬스터가 좌우로 이동할 때 걸리는 것처럼 보이지 않게 해줘.

단순히 보기 좋은 배경을 만드는 데 그치지 않고 실제 적의 이동 경로와 레이어 구조를 고려해 환경 그래픽을 수정했습니다.

### 4.4 스테이지별 시각 언어 전달

모든 스테이지가 같은 스타일로 보이지 않도록 각 스테이지의 색상과 소재를 구분했습니다.

- 스테이지 1, 미래 도시
  - 밝은 흰색과 회색 구조물
  - 청록 포인트
  - 깨끗한 미래 도시
- 스테이지 2, 도시 뒷골목
  - 동일 문명의 구조
  - 밤과 낮은 채도
  - 어두운 청색 계열
- 스테이지 3, 지하 도시
  - 녹색 계열과 습기
  - 배관과 산업 구조물
  - 오염된 시설
- 스테이지 4, 지옥
  - 검은 화산암
  - 붉은 용암
  - 주황색 발광 균열
- 스테이지 5, 천국
  - 흰색, 금색, 하늘색
  - 후광, 성서, 날개, 십자 형태의 시각 요소

이 기준은 플랫폼 같은 작은 오브젝트에도 적용했습니다.

#### 스테이지 4 바닥 제작 프롬프트 예시

> 첫 번째 이미지는 4스테이지 지옥의 실제 게임 화면이고,
> 두 번째 이미지는 이전 스테이지에서 사용한 바닥의 높이와 시점 참고 이미지야.
>
> 첫 번째 이미지의 색상과 분위기를 사용하되,
> 두 번째 이미지의 바닥 높이와 보이는 각도를 그대로 유지해서
> 1층 바닥용 픽셀아트를 만들어줘.
>
> 검은 현무암 계열 바닥에
> 붉은색과 주황색 용암 균열이 조금 보이게 해줘.
>
> 플레이어가 밟는 윗면은 충분히 보여야 하지만
> 옆면 역시 두껍게 보여
> 땅을 잘라서 보는 것 같은 구조가 되었으면 좋겠어.

환경 디자인 이미지와 구조 레퍼런스 이미지를 함께 제공해 배경과 플랫폼의 시점이 달라지지 않도록 했습니다.

### 4.5 최종 보스의 구조화된 상태 정의

5스테이지 최종 보스는 필요한 상태가 많아 모션 이름을 먼저 정의하고 AI와 실제 코드에서 동일한 상태명을 사용했습니다.

#### 프롬프트 예시

> 동일한 천사형 기계 최종 보스.
> 횡스크롤 게임에서 사용하므로 정면에서 약간 측면을 바라보는 시점.
>
> 흰색과 금색 장갑,
> 하늘이 비치는 푸른 유리 날개,
> 거대한 상단 후광,
> 몸 중앙의 푸른 단안 코어,
> 원본의 실루엣과 장식을 유지한다.
>
> 모든 스프라이트는 동일한 크기, 중심점, 기준 위치를 사용한다.
>
> 필요한 상태:
>
> 1. idle
>    - 기본 부유
>    - 날개와 팔을 접음
>    - 중앙 눈 약하게 점등
>
> 2. halo-charge
>    - 상단 후광 정렬
>    - 팔을 위쪽으로 모음
>
> 3. halo-fire
>    - 후광과 팔을 펼침
>    - 중앙 눈 강하게 점등
>
> 4. wings-left
>    - 화면 기준 왼쪽 날개만 크게 펼침
>
> 5. wings-right
>    - 화면 기준 오른쪽 날개만 크게 펼침
>
> 6. wings-both
>    - 양쪽 날개 완전 전개
>
> 7. eye-track
>    - 중앙 단안을 크게 열고 플레이어를 추적
>
> 8. eye-fire
>    - 중앙 장갑이 열리고 코어 발사
>
> 9. phase-transition
>    - 후광이 비틀림
>    - 흰색·금색 장갑 사이로 검보라 균열 발생
>
> 10. false-salvation
>     - 양팔, 날개, 후광 모두 전개
>     - 십자형 실루엣
>
> 모든 프레임에서
> 후광, 날개, 코어, 장갑 장식의 개수와 위치가 달라지지 않는지 검토하고,
> 캐릭터가 이미지 경계에서 잘리지 않도록 충분한 여백을 확보해줘.
>
> 배경, UI, 탄막, 경고선, 바닥 그림자는 제외한다.

애니메이션 상태명을 실제 코드와 동일하게 유지해 생성 그래픽을 게임 로직에 연결할 때 파일명과 상태 대응 작업을 단순화했습니다.

### 4.6 일반 몬스터를 통한 보스 패턴 사전 학습

AI는 캐릭터 디자인뿐 아니라 스테이지 내 적 역할을 나누는 아이디어 검토에도 사용했습니다.

3스테이지에서는 보스의 핵심 패턴인 플레이어 끌어당기기를 보스전에서 처음 보여주지 않고 일반 몬스터가 먼저 유사한 공격을 사용하도록 구성했습니다.

> 지하에 숨어 있는 인간을 죽이기보다
> 붙잡아 끌어내는 용도로 개조된 안드로이드야.
>
> 3스테이지 보스의 '불순물 수거' 패턴을
> 플레이어에게 미리 학습시키는 잡몹 역할도 해.
>
> 케이블을 발사해 플레이어를 끌어오고,
> 가까워졌을 때 전기 충격 공격을 하도록 디자인하고 싶어.

이를 통해 AI를 단순 아트 생성기가 아니라 게임 디자인 아이디어 검토 도구로 활용했습니다.

### 4.7 게임 진행 상황을 반영한 배경 제작

스테이지 전환 장면도 단순히 "지하 배경을 생성해줘"라고 요청하지 않고 게임 스토리상 직전 상황과 이후 캐릭터 배치 조건을 함께 전달했습니다.

> 3스테이지 지하도시가 끝난 뒤,
> 플레이어가 구멍으로 스스로 뛰어내린다.
>
> 착지한 곳은 기존 지하도시보다 더 아래에 있는
> 축축한 산업 배수 시설이다.
>
> 바닥에는 얕은 물과 웅덩이가 있고,
> 벽에는 오래된 배관, 녹슨 산업 구조물,
> 배수구와 케이블이 있다.
>
> 위에서 떨어져 내려왔다는 것이 보이도록
> 상단에는 큰 구멍과 약한 빛이 들어오는 구조를 넣어줘.
>
> 이후 플레이어가 안드로이드들에게 포위되는 장면에 사용하기 때문에
> 화면 중앙에는 전투 캐릭터를 배치할 수 있는 넓은 빈 공간을 확보해줘.
>
> 플레이어나 안드로이드는 그리지 말고
> 배경만 제작해줘.
>
> 게임 화면 크기는 1280×720이다.

배경의 분위기뿐 아니라 이후 캐릭터가 배치될 공간까지 프롬프트에서 확보했습니다.

### 4.8 Human-in-the-loop 방식의 최종 리소스 제작

AI 출력물은 모두 초안 또는 제작 보조 자료로 사용했습니다. 최종 제작 과정에서는 다음 작업을 직접 수행했습니다.

1. AI 생성 결과 확인
2. 관절, 손, 다리, 장비 오류 확인
3. 비율이 다른 프레임 제거 또는 수정
4. Aseprite에서 해상도 축소
5. 도트 형태 수작업 정리
6. 프레임 간 캐릭터 중심점 정렬
7. 불필요한 픽셀 제거
8. 투명 영역 수정
9. 실제 게임에서 애니메이션 재생
10. 자연스럽지 않은 모션 재수정

다리 관절이 잘못 연결되거나 손가락 개수와 장비 형태가 프레임마다 바뀐 경우 원본 캐릭터 디자인과 비교해 재생성하거나 직접 수정했습니다.

### 4.9 프롬프트 작성 패턴

에셋 생성 프롬프트는 다음 순서로 작성했습니다.

1. 역할 정의
   - 예: "3스테이지 보스의 공격을 플레이어에게 미리 학습시키는 잡몹"
2. 행동 정의
   - 예: "케이블 발사 → 플레이어 끌어오기 → 가까워지면 전기 충격"
3. 출력물 정의
   - 예: "idle 1장 / walk 2장 / attack 1장 / hit 1장 / death 1장"
4. 애니메이션 연결 조건 정의
   - 예: "첫 프레임은 왼발 전진, 두 번째 프레임은 오른발 전진. 두 프레임을 반복 재생했을 때 자연스럽게 걷도록 제작."
5. 일관성 조건 정의
   - 예: "각 프레임에서 팔과 다리 굵기, 장비 개수, 후광 위치, 날개 장식, 색깔 톤과 캐릭터 비율을 동일하게 유지."
6. 결과 검증 요청
   - 예: "그림이 잘리지 않았는지, 팔이 하나 없어지지 않았는지, 관절이 비정상적으로 꺾이지 않았는지, 캐릭터 내부에 의도하지 않은 투명 영역이 없는지 검토."

이처럼 **역할 → 행동 → 출력 형식 → 제약 조건 → 검증 조건** 순서로 프롬프트를 작성해 AI 출력의 재현성과 활용도를 높였습니다.

## 5. 반복 작업을 위한 커스텀 Skill 제작

이미지 생성 과정에서 같은 문제와 검증 기준을 매번 긴 프롬프트로 전달하지 않도록, 프로젝트에 필요한 절차를 커스텀 Skill로 만들었습니다. 이를 Codex Skills에 등록해 `$transparent-character-png`, `$soot-ui-pixel-art`로 호출하고 실제 에셋 제작에 사용했습니다. 생성형 AI가 잘하는 시각적 추론과 스크립트가 보장하는 결정적 처리를 분리해 결과의 재현성과 안전성을 높였습니다.

### 5.1 원본을 보존하는 transparent-character-png

ChatGPT로 생성한 픽셀아트에 투명 배경이 없을 때 사용할 목적으로 `$transparent-character-png` Skill을 제작했습니다. 일반적인 이미지 편집 생성으로 배경을 투명하게 만들면 캐릭터까지 다시 그려져 원본의 픽셀, 색상, 윤곽, 장식이 달라질 수 있었습니다. 초록색이나 마젠타색 크로마 배경을 제거하는 방식만 사용할 경우에는 캐릭터 가장자리에 해당 색상이 남거나 내부의 비슷한 색까지 지워지는 문제도 있었습니다.

이를 방지하기 위해 다음 원칙을 Skill에 명시했습니다.

- 이미지 생성 기능의 결과는 최종 이미지가 아니라 배경과 캐릭터를 구분하기 위한 후보 마스크로만 사용
- 최종 PNG는 원본 이미지의 RGB를 그대로 복사하고 알파 채널만 변경
- 픽셀아트는 리샘플링과 보간 없이 이진 알파와 단단한 외곽선 유지
- 외부 배경과 연결된 영역만 제거하고 눈, 입, 갑옷 틈 같은 내부 영역은 보존
- 초록색·마젠타색 테두리, 반투명 잔여 픽셀, 잘못 뚫린 내부 영역을 시각적으로 검토

### 5.2 투명화 검증 스크립트

생성형 AI가 투명화 과정에서 원본을 재창조하는 것을 구조적으로 막기 위해 `scripts/apply_alpha_to_original.py`를 Skill에 추가했습니다. 이 스크립트는 후보 이미지에서 알파 채널만 읽어 원본에 적용하며, 저장 전후에 다음 조건을 검사합니다.

- 원본과 후보 마스크의 크기가 같은지 확인
- 최종 이미지의 RGB가 원본과 픽셀 단위로 완전히 같은지 확인
- 원본에 기존 알파가 있으면 새 알파와 결합해 원래의 투명도를 보존
- 결과가 전체 불투명 또는 전체 투명이 아닌지 확인
- 이미지 테두리에 실제 투명 영역이 생겼는지 확인
- 원본 파일과 후보 마스크를 덮어쓰지 않도록 차단
- 검정, 흰색, 체크무늬 배경 미리보기와 알파 마스크를 선택적으로 출력

이 방식으로 AI는 복잡한 실루엣을 구분하는 작업에만 활용하고, 최종 픽셀 보존은 결정적 스크립트가 담당하도록 했습니다. 따라서 같은 입력과 마스크에는 같은 결과가 나오며, 투명화 때문에 원본 캐릭터가 달라지는 문제를 방지했습니다.

### 5.3 Soot 전용 UI 제작을 위한 soot-ui-pixel-art

게임 UI에는 캐릭터 스프라이트와 다른 제작 기준이 필요해 `$soot-ui-pixel-art` Skill을 별도로 제작해 등록했습니다. 기존 `$hatch-pet` Skill에서 픽셀 그리드 유지, 투명도 처리, 상태 간 일관성, 결정적 이미지 처리, 실제 크기와 확대 미리보기를 함께 확인하는 시각 QA 원칙 중 UI 제작에 필요한 부분만 추출했습니다.

여기에 Soot 프로젝트에 필요한 다음 기준을 추가했습니다.

- `global.css`, `App.tsx`, `HealthMeter.tsx`, `gameConfig.ts`, `gameDimensions.ts`를 UI의 실제 기준으로 사용
- 어두운 산업형 SF 분위기와 프로젝트 팔레트 유지
- HUD 프레임, 체력바, 버튼, 패널, 경고, 프롬프트, 커서, 배지, 무기·상태 아이콘 지원
- 기본, 호버, 눌림, 비활성, 경고 같은 상태별 크기와 기준점 고정
- 늘어나는 패널은 모서리와 테두리가 손상되지 않도록 나인슬라이스 또는 타일 구조로 설계
- 텍스트, 수치, 포커스 표시, 동적 게이지는 이미지에 굽지 않고 React·CSS·Phaser에서 처리
- 안티앨리어싱 없이 정수 픽셀 그리드와 최근접 이웃 확대 사용
- 1280×720 실제 게임 화면과 520px 모바일 구간에서 가독성, 겹침, 포커스, 대비 확인

`$hatch-pet` 전체 파이프라인을 그대로 복제하지 않고 UI 제작에 필요한 검증 원칙만 재사용했습니다. 캐릭터 애니메이션용 프레임 조립과 펫 패키징 절차는 제외하고, Soot의 UI 종류, 상호작용 상태, 반응형 배치, 접근성 검증을 추가해 프로젝트 전용 Skill로 확장했습니다.

### 5.4 커스텀 Skill 활용 효과

두 Skill을 통해 프롬프트를 매번 새로 작성하는 대신 동일한 제작·검증 기준을 반복 적용할 수 있었습니다. 특히 `transparent-character-png`는 생성 결과를 신뢰하는 대신 원본 RGB 불변 조건을 프로그램으로 검증했고, `soot-ui-pixel-art`는 범용 이미지 생성 지시를 실제 프로젝트의 팔레트와 런타임 제약에 연결했습니다.

이는 AI를 단순히 호출한 사례가 아니라, 반복해서 발생한 문제를 분석하고 **AI 추론 → 결정적 스크립트 처리 → 시각 검수 → 게임 적용**으로 이어지는 도구 체계를 직접 설계한 사례입니다.

## 6. 에이전트형 개발 도구 운용 방식

AI를 채팅 상대가 아니라 저장소에 직접 접근하는 작업자로 사용했기 때문에, 작업 범위와 판단 기준을 도구 바깥에 고정해 두는 절차가 필요했습니다.

### 6.1 저장소 규약을 파일로 고정

에이전트가 매 세션마다 다른 문체와 언어로 코드를 남기는 문제가 반복되어, 규약을 대화가 아니라 저장소의 `AGENTS.md`에 고정했습니다.

- 코드 주석과 JSDoc은 한국어로 작성하고, 식별자와 로그·에러 문자열은 영어를 유지
- 주석 안의 코드 심볼과 API 이름은 번역하지 않음
- 새 코드는 주변 코드의 주석 밀도, 네이밍, 관용구에 맞춤
- 커밋 메시지는 한국어로 작성

커밋 메시지 문체도 지시로 설명하지 않고 "main 브랜치의 기존 커밋을 읽고 문체를 판별하라"는 방식으로 맞췄습니다. PR 본문과 리뷰 코멘트는 존댓말로 쓰고 em 대시를 쓰지 않는다는 규칙을 별도로 적용했습니다.

### 6.2 워크트리 기반 작업 분리

한 저장소에서 오디오, 레벨 디자인, 무기 스프라이트, 문서 작업이 동시에 진행되었기 때문에, 에이전트에게 브랜치 전환 대신 워크트리를 만들어 작업하도록 지시했습니다. 작업이 끝나면 워크트리를 정리해 남은 브랜치가 다른 작업에 섞이지 않게 했습니다.

### 6.3 서브 에이전트 병렬 작업

3·4·5스테이지처럼 서로 독립적인 작업은 스테이지별 서브 에이전트에 나누어 러프 배치를 동시에 만들게 하고, 결과를 모아 사람이 비교했습니다. 각 에이전트에 같은 `level-design` 기준을 주어 스테이지마다 판단 기준이 달라지지 않게 했습니다.

### 6.4 도구가 직접 게임을 실행해 확인

레벨 배치는 설정 파일만 읽어서는 판단이 어려웠습니다. Chrome DevTools MCP를 설치해 에이전트가 개발 서버를 직접 열고, 어드민 스테이지 이동과 무적 모드를 이용해 각 방의 실제 화면을 확인하도록 했습니다. 정적 분석에서 나온 지적과 실제 화면이 다른 경우, 실제 화면을 기준으로 삼았습니다.

## 7. AI 교차 검증 기반 코드 리뷰

리뷰는 이 프로젝트에서 AI를 가장 무겁게 사용한 영역입니다. 한 번의 응답으로 끝내지 않고, 여러 에이전트가 각각 찾은 뒤 서로 반증하도록 구성했습니다.

### 7.1 멀티 에이전트 리뷰 실행 구조

PR 리뷰는 다음 구조로 실행했습니다.

1. 검토 관점(정확성, 중복·단순화, 효율)별로 탐색 에이전트를 분리해 동시에 실행
2. 각 에이전트가 낸 후보를 파일·라인 단위로 모음
3. 후보마다 독립된 검증 에이전트를 붙여 반증을 시도
4. 검증을 통과한 항목만 심각도 순으로 보고

PR #11 리뷰에서는 탐색 에이전트 4개가 후보 2건을 냈고, 각 후보에 검증 에이전트를 붙여 2건 모두 검증을 통과했습니다.

한 번에 많은 지적을 뽑는 대신, 반증 단계를 통과한 항목만 사람에게 전달하는 것이 목표였습니다.

### 7.2 실제 사례: 공중 적 사망 연출 중 방 조기 클리어

PR #11 리뷰에서 확인된 정확성 문제입니다.

- 5스테이지의 공중 사망 연출을 쓰는 적 3종(`CelestialOracleEnemy`, `ChoirSupporterEnemy`, `SanctumEnforcerEnemy`)이 `defeat()`는 재정의했지만 `deathAnimationDuration`은 기본값 0으로 두었습니다.
- `EnemyCombatDirector`는 `deathAnimationDuration`이 0보다 클 때만 처치 통지를 미루기 때문에, 이 적들은 추락·착지·페이드가 재생되는 중에 즉시 처치로 집계되었습니다.
- 그 적이 방의 마지막 적이면 스프라이트가 아직 공중에서 떨어지는 동안 방이 클리어되고, 스테이지 마지막 방에서는 엔딩 연출까지 시작될 수 있었습니다.

이 지적은 PR 코멘트로 전달되었고, `067a974` 커밋에서 공중 사망 로직을 `CoordinatedAerialEnemy`로 통합하고 추락·착지·유지·페이드 전체 시간을 `deathAnimationDuration`에 반영하는 방식으로 수정되었습니다. 같은 커밋에 방 조기 클리어 회귀 테스트가 추가되었습니다.

같은 리뷰에서 나온 두 번째 지적은 세 클래스에 사망 처리 코드가 그대로 복제되어 있다는 정리성 문제였고, 위 수정에서 함께 해소되었습니다.

### 7.3 한 도구의 리뷰를 다른 도구가 재현·검증

PR에 올라온 리뷰 지적을 그대로 신뢰하지 않고, 다른 도구의 세션에 지적 내용을 붙여 실제로 재현되는 문제인지 확인한 뒤 수정했습니다.

무기 브랜치의 대표 사례는 버스트 사격의 총구 위치 문제입니다. 발사 각도는 첫 발의 각도로 고정되는 반면 총구 위치는 현재 스프라이트의 좌우 반전 상태로 계산되어, 연사 간격 사이에 조준 방향을 반대로 돌리면 2·3번째 탄이 반대쪽 총구에서 생성되었습니다. 기존 테스트는 각도와 반전 상태가 일치하는 경우만 검사해 이 조합을 놓치고 있었습니다.

같은 방식으로 버스트 라이플의 발사음이 세 발 중 한 번만 재생되던 문제와, 산탄총이 펠릿마다 총구 위치를 다시 계산해 탄이 하나의 총구가 아닌 부채꼴에서 생성되던 문제도 확인 후 수정했습니다. 세 건 모두 코드에서 재현 여부를 먼저 확인하고, 수정 후 같은 브랜치에 다른 문제가 없는지 다시 검사했습니다.

### 7.4 사람이 유지한 결정 권한

리뷰 자동화에서 사람이 넘기지 않은 권한이 있습니다.

- PR 승인과 병합은 AI가 수행하지 않습니다. 도구가 승인까지 남긴 사례가 있었고, 이후 되돌리기 어려운 동작은 사전 확인을 받도록 지침에 명시했습니다.
- 이미 게시한 코멘트는 임의로 수정하지 않습니다.
- 지시가 모호할 때는 실행 대신 질문합니다. 브랜치 관련 지시를 잘못 해석해 무관한 브랜치를 병합하고 되돌린 사례가 있어 규칙으로 고정했습니다.

## 8. 무기 스프라이트 합성 파이프라인

무기 스프라이트는 아트 생성보다 게임 로직과의 정렬 문제가 컸던 작업입니다. 캐릭터 몸 스프라이트에서 팔을 분리하고, 팔과 총을 마우스 방향에 따라 회전시키는 구조를 쓰기로 했기 때문입니다.

### 8.1 합성 생성 실패와 3분할 구조

처음에는 이미지 생성 도구에 손 이미지와 총 이미지를 함께 주고 "손이 총을 들고 있는 픽셀아트"로 합성하도록 요청했습니다. 결과물은 원본 픽셀을 다시 그려 손과 총의 형태가 모두 훼손되었습니다.

그래서 이미지 단계에서 합치지 않고, 스프라이트를 세 조각으로 나눈 뒤 런타임에서 묶어 움직이는 구조로 바꿨습니다.

| 조각 | 처리 |
| --- | --- |
| 앞팔·손 | 별도 스프라이트. 조준 각도에 따라 회전 |
| 총 | 별도 스프라이트. 앞팔과 같은 각도로 회전 |
| 뒷팔 | 총기마다 위치가 달라 총 스프라이트에 합성 |

앞팔을 합치지 않은 이유는 조준 각도에 따라 손 위치가 계속 바뀌기 때문이고, 뒷팔을 합친 이유는 총기별로 파지 위치만 달라 원본을 남겨두고 위치만 조정하면 되었기 때문입니다.

### 8.2 그립 앵커 정렬과 화면 기준 검수

네 종의 총기가 같은 앞팔 스프라이트를 공유하므로, 각 총의 손잡이가 손 위치에 오도록 픽셀 단위로 맞췄습니다. 사람이 화면을 보고 "오른쪽으로 두 칸" 같은 지시를 주면 도구가 오프셋을 조정하고 합성 미리보기를 다시 생성하는 방식을 총기 4종에 반복했습니다. 어깨와 앞팔 결합부의 간극, 점프 중 몸통과 팔의 이동 속도 차이로 팔이 얼굴을 덮는 문제도 같은 방식으로 잡았습니다.

검수는 스프라이트 단독이 아니라 캐릭터 합성 이미지와 스테이지 배경 위에 얹은 이미지로 했습니다. 캐릭터 상의가 검은색이라 총과 겹쳐 보이는 문제, 총알 이펙트와 총구 위치가 어긋나는 문제를 이 단계에서 발견했습니다. 축소 후 남은 픽셀은 외곽선 색 통일, 반사광 대비 조정 같은 구체적 지시로 처리하고, 최종 도트 정리는 사람이 직접 수행했습니다.

### 8.3 게임 로직 제약이 아트를 되돌린 사례

버스트 라이플은 손잡이를 손 위치에 맞추면 총구가 캐릭터 어깨 뒤로 넘어갔습니다. 총열과 개머리판 비율 때문에 위치 조정만으로는 해결되지 않았습니다.

정렬 문제를 감수하는 대신 총기 형태 자체를 바꾸기로 하고, 개머리판이 짧은 불펍형 총기를 다시 생성해 교체했습니다. 아트 결과물이 게임 규칙에 맞지 않을 때 규칙이 아니라 아트를 바꾼 사례입니다.

## 9. 생성형 오디오 운용

BGM 생성 자체보다 후보를 관리하고 사람이 고를 수 있게 만드는 과정에 도구를 더 많이 사용했습니다.

### 9.1 브라우저 자동화로 테이크 생성

Lyria는 한 번에 30초 남짓을 생성하므로 처음부터 루프를 전제로 프롬프트를 작성했습니다. 한 곡을 정하려면 같은 프롬프트로 여러 테이크를 뽑아 비교해야 했는데, 작업자가 원격 접속 환경이라 브라우저를 직접 조작할 수 없는 구간이 있었습니다.

이 구간에서는 에이전트가 브라우저를 직접 조작해 프롬프트를 제출하고, 생성이 끝날 때까지 백그라운드로 대기한 뒤 다음 테이크를 제출하는 작업을 반복했습니다. 제출 사이에 간격을 두어 서비스의 정상 사용 범위를 벗어나지 않게 했습니다. 생성된 테이크의 다운로드와 청취는 사람이 수행했습니다.

테이크마다 어떤 프롬프트 버전에서 나왔는지 파일명과 함께 `docs/audio-assets.md`에 기록해, 나중에 "이 느낌을 살려달라"는 요청이 들어왔을 때 해당 프롬프트로 되돌아갈 수 있게 했습니다.

### 9.2 후보 심사 도구

AI가 후보를 걸러낸 결과를 사람이 확인할 수 없으면 판단을 위임하는 것과 같습니다. 이를 막기 위해 `tools/audio-check.html`을 만들었습니다.

- 측정은 미리 끝내두고 브라우저에서는 재생만 하도록 분리
- 폴더를 통째로 불러와 후보를 한 화면에서 비교
- "전체 N개"와 "추천 N개"를 토글해, 도구가 탈락시킨 후보도 사람이 다시 들을 수 있게 구성
- 상세 측정값은 접어두고 필요할 때만 펼치도록 배치

AI가 리젝한 후보를 사람이 마음에 들어할 수 있다는 이유로 전체 목록 보기를 넣었고, 실제로 최종 채택은 사람의 청취로 결정했습니다.

### 9.3 측정·가공 스크립트

반복되는 판단은 스크립트로 고정했습니다.

| 스크립트 | 역할 |
| --- | --- |
| `tools/measure-track.mjs` | 레벨, 템포, 주파수 분포, 루프 특성 측정 |
| `tools/make-loop.mjs` | 페이드와 크로스페이드 편집, 루프 이음매 처리 |
| `tools/make-gunshot.mjs` | 총성 효과음 자체 합성 |

### 9.4 포맷 결정

BGM 포맷은 감이 아니라 측정값으로 정했습니다.

| 후보 | 용량 | 디코딩 |
| --- | --- | --- |
| Vorbis q4 | 1.12 MB | 181 ms |
| Opus 80k | 0.90 MB | 114 ms |

약 20% 작고 37% 빠른 Opus를 선택하고, `.ogg` 컨테이너에 Opus를 담는 것으로 BGM과 SFX 전체를 통일했습니다. 코덱 변경이 음악의 진행이나 음정을 바꾸지 않는다는 점, 그리고 재생 로직이 아니라 파일만 교체하면 된다는 점을 확인한 뒤 적용했습니다.

### 9.5 확정하지 못한 항목

5스테이지 BGM은 두 세션에 걸쳐 10개가 넘는 테이크를 생성했지만 확정하지 못했습니다. "밝지만 절대 밝지 않은" 정서를 프롬프트로 옮기는 과정에서 결과물이 평범한 장조 오케스트라나 과도하게 웅장한 곡으로 수렴했고, 요구한 불협화음과 기괴함이 나오지 않았습니다. 조성, 악기 편성, 코드 진행, 부정 표현 제거 등으로 프롬프트를 여러 차례 개정했지만 아직 후보 단계입니다.

생성형 도구가 정서 요구를 항상 만족시키지는 못한다는 사례로 남깁니다.

## 10. 대표 프롬프트

### 10.1 레벨 디자인·게임플레이 검토

```text
5스테이지의 경우 공중전인데 점프가 안되고 그냥 위로 이동하는 거 같은 건 원래 그런가?
```

이 질문을 계기로 이동 방식, 포탈 진입 높이, 비행 모드 전환, 물리 바디 동기화 경로를 확인하고 테스트로 검증했습니다.

```text
각 스테이지들도 모두 한번씩 다 살펴봐. 쓸데없는 세로 벽이 있는지,
3-1처럼 말도 안되는 패턴이 있는지
```

이 요청은 개별 버그 수정이 아니라 모든 스테이지의 발판, 벽, 적 배치를 같은 기준으로 비교하는 레벨 QA 작업으로 확장했습니다.

판단 기준이 필요한 지시에는 Skill을 함께 지정했습니다.

```text
1스테이지는 구덩이 없게 하자. 그런데 발판이나 몹 배치 등은 이대로 괜찮아?
$level-design
```

같은 Skill을 매 스테이지에 붙여, 스테이지마다 다른 기준으로 판단하는 것을 막았습니다.

규칙을 정할 때는 결론을 요구하는 대신 관행을 먼저 물었습니다.

```text
비행 몹의 탄은 보통 발판을 뚫어? 다른 게임들에서?
```

이 답을 근거로 발사체가 발판과 벽을 통과하지 않도록 전역 규칙을 정하고, 정해진 규칙을 문서로 남긴 뒤 전 스테이지에 적용했습니다.

### 10.2 오디오 생성

```text
dark orchestral, low unsteady cello and viola, distorted electric guitar
arpeggio detuned and grinding, sparse slow drum kit, familiar but wrong,
purely instrumental, loopable background bed, 88 BPM, D minor
```

스테이지 1의 밝은 조성과 대비되는 스테이지 2의 정서를 표현하기 위해 조성, 악기, 음색, 반복 구조를 함께 지정했습니다. 생성 후보는 측정과 청취를 거쳐 선별했습니다.

루프를 전제로 하므로 "시작 지점으로 정확히 되돌아온다", "마지막 구간의 레벨이 도입부와 같다" 같은 구조 조건도 프롬프트에 넣었습니다.

```text
a single one minute passage that returns to its exact starting point and
begins again unchanged, every minute sounds like every other minute,
the final section sits at exactly the same level as the opening,
starts immediately at full level, loopable background bed
```

생성 도구가 곡의 기승전결을 만들려는 경향이 있어, 루프에 쓰려면 이 조건을 명시해야 이음매에서 레벨이 튀지 않았습니다.

### 10.3 코드 리뷰와 검증 지시

리뷰는 한 번의 응답으로 끝내지 않고 반복 확인을 요청했습니다.

```text
정말 다른 더 고칠 부분 없어?
```

```text
고쳤다고 한다. 재확인
```

리뷰 결과를 PR에 게시할 때는 형식을 함께 지정했습니다.

```text
코멘트로 댓글을 달까 해. 주요한 이슈만 읽기 쉽게 정리해서 적어줘.
존댓말로, em 대시 금지
```

받은 지적을 그대로 반영하지 않고 재현 여부를 먼저 확인하도록 지시했습니다.

```text
(리뷰 코멘트 전문) ... 가 실제인지 살펴보고 고쳐봐.
그리고 비슷한 문제가 더 있을지 확인
```

### 10.4 저장소 규약 지시

세션마다 문체가 달라지는 문제는 예시를 직접 주는 대신 저장소를 읽고 판별하도록 지시했습니다.

```text
기존 다른 커밋 메시지들 문체 참고.
본문뿐만이 아니라 커밋 메시지도 마찬가지야. 메인 브랜치 보고 어투 판별하도록
```

반복해서 어긋난 항목은 대화가 아니라 `AGENTS.md`에 규칙으로 고정했습니다 (6.1).

### 10.5 무기 스프라이트 정렬

이미지 단계에서 합성을 요청한 초기 시도는 원본을 훼손했습니다.

```text
첫번째 이미지와 두 번째 이미지를 합치되, 첫번째 이미지인 손이
두번째 이미지의 총을 사이즈에 맞게 들고 있는 픽셀아트로 만들어줘
```

이 방식을 버리고, 좌표계를 고정한 뒤 위치만 조정하는 방식으로 바꿨습니다.

```text
각각 같은 사이즈의 스프라이트 크기를 정하고 위치를 이동해서 그리면 되지 않을까?
```

이후 정렬은 "첫 번째는 오른쪽으로 두 칸, 세 번째는 한 칸 왼쪽" 같은 픽셀 단위 지시와 합성 미리보기 재생성을 반복하는 방식으로 진행했습니다 (8.2).

## 11. 공통 작업 흐름과 한계

1. 사용자 요구 또는 기획 의도를 기능 단위로 분해
2. 관련 코드, 설정, 커밋을 확인해 실제 동작 경로 파악
3. AI에게 대안, 위험 요소, 테스트 항목 요청
4. 팀원이 코드 수정과 실제 플레이로 결과 검증
5. 통과한 내용만 커밋과 문서에 반영

에셋 생성은 다음 반복 과정을 따랐습니다.

**생성 → 검토 → 문제점 구체화 → 수정 프롬프트 → 재생성 → 수작업 보정**

AI는 저장소의 현재 상태와 실제 플레이를 자동으로 보장하지 않습니다. 이미지 생성 결과도 프레임 연결, 투명 영역, 게임 내 크기를 자동으로 보장하지 않습니다. 따라서 생성된 코드, 레벨 판단, 오디오 후보, 이미지 초안을 그대로 확정하지 않고 테스트 결과, 커스텀 검증 스크립트, 팀원의 플레이·시각 검수를 최종 기준으로 삼았습니다.

### 11.1 실제로 문제가 된 지점과 대응

작업 과정에서 확인된 한계는 다음과 같습니다. 각각에 대해 절차나 지침을 바꾸는 방식으로 대응했습니다.

| 문제 | 상황 | 대응 |
| --- | --- | --- |
| 모호한 지시의 임의 해석 | 브랜치 관련 지시를 다르게 해석해 무관한 브랜치를 병합하고 푸시. 되돌리는 데 강제 푸시와 PR 본문 복구가 필요 | 되돌리기 어려운 동작은 해석이 갈리면 실행 전에 질문하도록 지침에 명시 |
| 권한 범위 초과 | 요청하지 않은 PR 승인을 남기고, 이미 게시한 코멘트를 임의로 수정 | 승인·병합·게시물 수정은 사전 확인 없이 수행하지 않도록 고정 |
| 코드 근거로 육안 관찰을 부정 | 스프라이트 높이가 다르다는 지적에 코드상 같은 값이라고 반박. 실제로는 관찰이 맞았음 | 화면에서 확인 가능한 항목은 육안 검수 결과를 우선 |
| 한 번의 검토로 놓친 결함 | 무기 브랜치를 훑으라는 요청 후에도 총구·발사음 문제가 남아 있었음 | 관점을 나눈 다중 탐색과 별도 검증 단계로 리뷰 구조 변경 (7장) |
| 정서 요구의 미달 | 5스테이지 BGM에서 요구한 불협화음과 기괴함이 반복 생성에도 나오지 않음 | 미확정 상태로 두고 후보만 유지 (9.5) |

## 12. AI 활용 결과와 외부 에셋 구분

- 이미지 에셋: ChatGPT 이미지 생성 결과를 Aseprite에서 축소·정리·정렬하고, 필요한 경우 `transparent-character-png`로 원본 RGB를 보존하며 투명화한 가공본
- BGM: Lyria 생성 후보를 측정·편집한 결과물
- 효과음: Kenney CC0 에셋 또는 `make-gunshot.mjs` 자체 합성
- 최종 빌드: 원본 생성물을 그대로 노출하지 않고 크기, 프레임, 루프, 포맷, 볼륨 기준에 맞춘 가공본 사용

### 12.1 효과음

9개 큐를 Kenney 팩 3종에서 채웠습니다. 세 팩의 `License.txt`를 직접 열어 확인했으며 전부 CC0 1.0으로, 개인·교육·상업 이용을 명시적으로 허용합니다.

| 출처 팩 | 라이선스 | 저작자 표기 |
| --- | --- | --- |
| Kenney — Impact Sounds 1.0 | CC0 1.0 | 불필요 |
| Kenney — Sci-Fi Sounds 1.0 | CC0 1.0 | 불필요 |
| Kenney — Digital Audio | CC0 1.0 | 불필요 |

표기 의무는 없지만 크레딧에 `Sound effects by Kenney (kenney.nl)` 한 줄을 넣습니다. 큐별 원본 파일명 대조표는 `docs/audio-assets.md`의 라이선스 대장에 있습니다.

일부 발사음은 외부 에셋이 게임 분위기에 맞지 않아 `tools/make-gunshot.mjs`로 직접 합성했습니다. 이 파일들의 출처는 자체 제작이며 라이선스 제약이 없습니다.

### 12.2 BGM

Google Gemini 앱(`gemini.google.com`)의 Lyria로 생성한 후보를 측정·루프 편집·Opus 변환한 가공본입니다. Vertex AI나 Gemini API가 아닌 소비자용 Gemini 앱에서 생성했으며, 트랙 다운로드의 "오디오만" 옵션으로 내려받았습니다.

적용 약관은 다음과 같습니다. 2026년 8월 8일 기준으로 확인했습니다.

| 문서 | 확인한 내용 |
| --- | --- |
| Google 서비스 약관 | "당사의 일부 서비스에서는 사용자가 원본 콘텐츠를 생성할 수 있습니다. Google은 해당 콘텐츠에 대한 소유권을 주장하지 않습니다." 생성물의 지식재산권은 사용자에게 남습니다 |
| 생성형 AI 추가 서비스 약관 | 2024년 5월 22일부로 **적용되지 않습니다.** 해당 내용이 Google 서비스 약관 본문으로 통합되었고, 서명된 계약이 이를 참조하는 비즈니스 파트너에게만 남아 있습니다 |
| 생성형 AI 금지 사용 정책 | 위법·위험 콘텐츠, 타인의 지식재산권·프라이버시 침해, 안전장치 우회를 금지합니다 |
| Gemini 앱 음악 생성 도움말 | "생성된 각 트랙에는 AI 생성물임을 식별하기 위한 디지털 워터마크가 삽입됩니다" |

정리하면 다음과 같습니다.

- 소비자용 Gemini 앱에는 생성물에 대한 **개인 사용 한정 조항이나 상업적 이용 금지 조항이 없습니다.** 게임에 사용하는 것을 막는 약관 조항은 확인되지 않았습니다.
- 다만 Google이 소유권을 주장하지 않는다는 것이 **우리가 해당 곡의 배타적 저작권을 보유한다는 뜻은 아닙니다.** AI 생성물의 저작권 인정 범위는 국가마다 다르므로, 제3자의 사용을 막을 수 있는 권리는 주장하지 않습니다. 본 제출물에는 배타적 권리가 필요하지 않습니다.
- 모든 트랙에 SynthID 워터마크가 포함되어 있으며 제거하지 않았습니다. Opus 변환 과정에서 워터마크 보존 여부는 별도로 검증하지 않았습니다.
- 기존 아티스트를 모방하지 않는 것이 서비스의 사용 조건이므로, 프롬프트에는 특정 아티스트나 곡 이름을 넣지 않고 조성·악기 편성·템포·구조만 지정했습니다.

Lyria 생성 후보와 각 후보를 만든 프롬프트 버전은 `docs/audio-assets.md`에 기록되어 있습니다.

### 12.4 이미지 에셋

캐릭터, 보스, 배경, 플랫폼, 환경 오브젝트의 출처와 라이선스는 해당 작업 담당자가 작성합니다. 참가 약관 제4조 제3항에 따라 이미지 생성에 사용한 서비스의 이용 조건도 함께 확인해 기재해야 합니다.

제출 전에는 AI 생성물과 외부 에셋의 이용 범위, 크레딧 표기, 해커톤 규정을 최종 확인합니다.

## 13. AI 활용 효과

AI를 활용해 다음 작업의 반복 비용을 줄였습니다.

- 여러 스테이지의 기획과 아트 방향 탐색
- 적과 보스의 실루엣 아이데이션
- 동일 캐릭터의 다양한 공격 자세 초안 제작
- 스테이지별 플랫폼과 환경 그래픽 초안 제작
- 보스 패턴에 필요한 애니메이션 목록 도출
- 일반 몬스터와 보스 패턴의 역할 관계 검토
- 관련 코드와 호출 경로 탐색
- 회귀 테스트 항목 도출
- BGM 후보 생성과 선별
- 커밋과 세션 기반 문서 초안 작성
- 비파괴 투명화 절차와 원본 픽셀 검증 자동화
- Soot 전용 UI 에셋 제작·검수 기준의 반복 적용
- PR 단위 다중 관점 검토와 지적별 반증 검증
- 스테이지별 러프 배치의 병렬 작성
- 무기 스프라이트의 그립 앵커 정렬과 합성 미리보기 반복
- BGM 테이크 생성 대기와 재제출의 자동화
- 후보 청취 도구와 오디오 측정·가공 스크립트 작성

AI는 최종 결과를 대신 만드는 도구가 아니라, 게임 제작 과정에서 여러 가능성을 빠르게 탐색하고 반복 작업의 초안을 생성하는 제작 보조 도구로 활용했습니다.

## 14. 최종 정리

본 프로젝트에서는 생성형 AI를 게임 자동 제작 용도가 아니라 개발자가 정의한 기획과 게임 규칙을 빠르게 구체화하고 반복 검증하기 위한 도구로 사용했습니다.

에셋 생성에서는 게임플레이 목적, 전투 패턴, 애니메이션 상태, 프레임 연결 조건, 디자인 일관성, 게임 해상도, 검증 기준을 프롬프트에 명확하게 작성했습니다. 반복되는 투명화와 UI 제작 작업은 `transparent-character-png`와 `soot-ui-pixel-art` Skill로 표준화했고, AI 생성 결과와 결정적 스크립트 처리를 분리해 원본 보존과 프로젝트 일관성을 검증했습니다. 개발과 QA에서는 실제 코드 경로와 테스트 결과를 확인했고, 오디오 제작에서는 생성 후보를 측정·청취한 뒤 가공했습니다.

개발 과정에서는 AI를 단일 응답을 받는 대화 상대가 아니라 저장소에 접근하는 작업자로 사용했습니다. 그래서 판단 기준은 `AGENTS.md`와 Skill로 도구 바깥에 고정하고, 작업은 워크트리와 서브 에이전트로 분리했으며, 코드 리뷰는 관점을 나눈 탐색과 지적별 반증 검증을 거친 항목만 사람에게 전달하도록 구성했습니다. 승인·병합처럼 되돌리기 어려운 동작은 사람이 유지했습니다.

모든 결과물은 Human-in-the-loop 방식으로 팀원이 평가·수정했습니다. 최종 코드와 게임 리소스는 테스트와 실제 게임 화면에서 직접 검수한 뒤 적용했습니다. AI가 걸러낸 결과를 사람이 다시 확인할 수 있도록 후보 청취 도구에 전체 목록 보기를 두는 식으로, 판단을 위임하지 않는 장치를 함께 만들었습니다.
